## 1. Recommendation

Build one **TypeScript Next.js/React PWA whose Node server owns the request API**, with **self-hosted PostgreSQL + Drizzle/pg**, **Better Auth**, **private filesystem receipt storage**, **self-hosted Inngest**, and **AI SDK through the required 9router**. Keep the domain modules and their public interfaces from the architecture document. Use the existing Mac for development and propose one AWS EC2 host for deployment; this role split is an assumption for review. Run Next.js, PostgreSQL, Inngest, a separate Connect worker, Redis and 9router together on each target as needed; expose only Next.js over private Tailscale HTTPS. Remove Supabase entirely; do not replace it with another inactivity-pausing free database. Use Terraform throughout: the AWS provider owns cloud infrastructure, and `kreuzwerker/docker` owns runtime containers on both Mac and EC2 through a shared module (§6). AWS deployment conflicts with a guaranteed permanent $0 budget (§5).

The user has chosen self-hosted orchestration. Retain Connect as the worker boundary: it makes a persistent outbound connection to the private Inngest server without a callback endpoint. Its worker requires a long-running runtime; Vercel serverless functions are unsupported. [Inngest Connect](https://www.inngest.com/docs/durable-execution/deploying-functions/connect).

**Inherited MVP requirements:** single user (see the proposed small multi-user evolution below), $0 monthly service budget, PWA with offline capture, IDR-only MVP with currency-aware storage, double-entry postings, 9router for model routing, `propose_only` autonomy, configurable budget-period start, and receipt deletion seven days after approval. Self-hosting Inngest and removing Supabase are confirmed; replacement choices and persistence details remain proposals. This removes provider inactivity pausing, but local sleep, power loss and maintenance still affect availability. Host availability and deletion timing need review before implementation (§8).

### Backend decision: Next.js request API or a separate API application?

**Recommendation for review: keep the request API inside the self-hosted Next.js Node application for the MVP, while retaining the separate Connect worker.** The current requirements describe one owner using one PWA, with offline capture, transactional ledger writes and asynchronous receipt processing. They do not establish a need for an independently deployed API application. This recommendation concerns deployment ownership; business rules remain in the framework-independent domain modules defined by the architecture document.

Next.js documents Route Handlers as HTTP endpoints, while explicitly cautioning that its backend capabilities are not a full backend replacement. For this proposal, PostgreSQL supplies transactions and persistence, Better Auth supplies sessions, and Inngest plus Connect supplies durable execution. Next.js supplies the web request layer. [Next.js backend guide](https://nextjs.org/docs/app/guides/backend-for-frontend).

| Requirement / tradeoff | Next.js Node request API | Separate TypeScript API, using Fastify as an example |
|---|---|---|
| PWA and offline commands | Route Handlers expose an explicit HTTP contract for the IndexedDB outbox and browser reads. UI and request API ship together. | The same HTTP contract can live in Fastify; offline replay still needs idempotency and recovery. A separate process does not solve synchronization. |
| Ledger correctness | Thin entry points call domain modules with one Drizzle transaction for approval, postings, audit and replay records. | The same modules and transaction can run in Fastify. Splitting the HTTP application alone adds no financial correctness guarantee. |
| API tooling | Existing Zod schemas parse untrusted inputs at the entry points. | Fastify offers route schemas for validation and response serialization. Adopting it would require choosing compatible schema integration, plus maintaining another application. [Fastify validation](https://fastify.dev/docs/latest/Reference/Validation-and-Serialization/). |
| Deployment and capacity | One web artifact, health check and request-side pool; UI/API updates remain coupled. The Connect worker already runs independently. | UI/API releases, resource limits and process failures can be isolated. Another container needs its own lifecycle, health checks, configuration and database-pool budget. On the same EC2 host, both still share a host failure. |
| Other clients | Explicit HTTP endpoints can serve a future native client or bot. | A dedicated API can become the stable owner when several clients require independent release schedules. Additional clients alone do not require extraction. |

**Use Route Handlers for durable outbox replay**, with a documented command envelope, client-generated idempotency key, validated money strings, bounded multipart uploads and explicit retryable/permanent error responses. Keep compatible replay handling across deployments because an offline device may return with older commands. Server Actions can support online forms, but the outbox should not persist framework-generated action references: Next.js can regenerate their IDs between builds. Server Components should call authorized server-side domain/read functions directly, avoiding a loopback HTTP request to their own Route Handlers. [Action IDs and authorization](https://nextjs.org/docs/app/guides/data-security), [server-side fetching](https://nextjs.org/docs/app/guides/backend-for-frontend#server-components).

Keep `next/headers`, `next/cache` and Inngest imports outside domain modules. The Next.js adapter verifies the Better Auth session and provisioned owner, parses input, injects dependencies and calls a public module interface; the worker calls those same interfaces with its trusted execution context. Retain transaction-local RLS and all §3 checks. Next.js recommends a server-only data-access layer with authorization and minimal returned data for new projects; apply that responsibility at the existing module seams rather than adding pass-through repositories. Moving endpoints to Fastify would still require these checks. [Next.js data security](https://nextjs.org/docs/app/guides/data-security).

Keep one Better Auth instance and session store in the Next.js deployment initially. Better Auth also documents Fastify integration, so auth is not a reason this boundary cannot change. If extracting later, assign auth/session verification to the API owner and deliberately handle SSR cookie forwarding and revocation; never trust a client-supplied owner header. A reverse proxy can route `/api/*` to Fastify and page requests to Next.js under the same HTTPS origin, so a split need not introduce browser CORS. Separate browser origins would require deliberate cookie, CORS and trusted-origin configuration. [Better Auth Fastify integration](https://better-auth.com/docs/integrations/fastify), [Next.js external rewrites](https://nextjs.org/docs/app/api-reference/config/next-config-js/rewrites#rewriting-to-an-external-url).

Receipt uploads do not require a separate API. Configure proxy and application byte/time limits, MIME checks and private filesystem handling; the Server Action default 1 MB body limit is configurable and is not a universal Route Handler upload limit. Fastify's multipart plugin offers file streams if a measured upload requirement later warrants it. Keep AI calls, recurrence and deletion in Connect, beyond the request lifetime. [Server Action body limit](https://nextjs.org/docs/app/api-reference/config/next-config-js/serverActions#bodysizelimit), [Fastify multipart](https://github.com/fastify/fastify-multipart).

This topology uses a persistent Node server, so Vercel/lambda execution limits do not establish its limits. Streaming responses also do not by themselves require extraction; self-hosted Next.js supports streaming with appropriate proxy configuration. No dedicated bidirectional WebSocket feature is established by the current MVP; Inngest Connect's private WebSocket belongs to the worker topology. [Self-hosted streaming](https://nextjs.org/docs/app/guides/self-hosting#streaming-and-suspense).

**Revisit extraction when evidence shows** independent API releases are necessary, UI rendering and request traffic need separate capacity/failure isolation, several clients need a separately governed API lifecycle, or a concrete upload/connection protocol cannot fit the supported Next.js request layer. Measure the actual host first. No benchmark or cost comparison was run; another process may fit the same host, but it adds operating work and does not inherently lower AWS costs. Extraction should preserve the HTTP contract and domain interfaces, then move request adapters and auth ownership deliberately.

### Scaling path: a small multi-user application

**Keep Next.js + PostgreSQL + the separate Connect worker for this stage.** This is a recommendation, not a capacity guarantee or authorization to implement multi-user access. Next.js documents multiple self-hosted instances; a separate Fastify application is not a prerequisite for growth. The existing §3 fixed-owner controls remain the MVP proposal until deliberately replaced. [Next.js self-hosting](https://nextjs.org/docs/app/guides/self-hosting).

**1. Make ownership correct before admitting another user.** For independent personal accounts, propose one financial owner per authenticated user; shared household/team workspaces would require a separately agreed membership/role model. Replace the single allowed-subject mapping with controlled provisioning of stable application owner UUIDs. Resolve the session to that owner on every request, then authorize every Account, Transaction, AgentProposal and Attachment lookup. Keep fail-closed, transaction-local RLS, scoped runtime roles and tenant-scoped uniqueness/idempotency; test user A attempting reads, writes and receipt downloads using user B's IDs. Better Auth supplies session identity; PostgreSQL supplies row policies, neither establishes this product's ownership rules automatically. [Better Auth sessions](https://better-auth.com/docs/concepts/session-management), [PostgreSQL RLS](https://www.postgresql.org/docs/current/ddl-rowsecurity.html).

Jobs must also stop deriving a fixed configured owner. Emit authoritative record IDs from an authorized producer; resolve their ownership through a narrowly scoped trusted lookup, validate any event owner against that record, then enter the correct transaction context. Define that bootstrap lookup explicitly so it neither requires an unknown tenant context nor grants workers unrestricted financial access. Scheduled reconciliation must enumerate eligible owners through an equally scoped path. Namespace offline commands and snapshots by owner, retain that identity through retries, and block replay across logout/account changes; clear read caches and explicitly handle unsynced captures. These are proposed application controls, extending §3–4.

**2. Measure one host before distributing it.** Agree active-user/concurrent-session assumptions, peak replay bursts, uploads per day and size, AI processing demand, acceptable p95 request/queue latency, availability and recovery targets. No DAU threshold or requests-per-second capacity has been measured. Monitor request errors/latency, pool waits, query/lock time, CPU/memory/disk, queue age and receipt-expiry lag; configure alerts against the agreed targets before release. Increase a measured host bottleneck first when appropriate. Host resizing improves capacity; redundant failure domains and tested failover address availability.

Budget connections across **all web replicas + all workers + authentication pools (if separate) + migrations/operations**, leaving administrative headroom below the database limit. Do not allocate a full default pool to every replica without recalculation. Start with one PostgreSQL writer; inspect slow plans, use owner-leading indexes matched to actual queries, bounded date ranges and stable cursor pagination for ledger history. PostgreSQL notes that large offsets still compute skipped rows. Add a pooler or read replicas only when measured demand warrants their transaction/read-consistency tradeoffs. [node-postgres pool sizing](https://node-postgres.com/guides/pool-sizing), [multicolumn indexes](https://www.postgresql.org/docs/current/indexes-multicolumn.html), [pagination ordering/cost](https://www.postgresql.org/docs/current/queries-limit.html).

**3. Scale AI work within its real quota.** Bound upload size/count, pending work and per-user daily inference allowance; enforce both global/provider capacity and per-user concurrency so one import cannot monopolize extraction. Inngest supports keyed concurrency and queues excess steps; concurrency limits simultaneous execution, not daily usage. Maintain application usage accounting/admission and backpressure, visible pending states and bounded retries; quota exhaustion must preserve manual entry and never trigger paid fallback. More workers do not increase provider quota or a local model's throughput. [Inngest concurrency](https://www.inngest.com/docs/durable-execution/flow-control/concurrency).

Add Connect worker replicas only after queue age and resource measurements justify them; retain idempotent effects and recalculate pools. Connect supports multiple worker connections and per-worker concurrency. **Worker replication is distinct from orchestration HA:** do not clone the proposed single-node SQLite + Redis Inngest container or share its SQLite file across hosts. A distributed Inngest/persistence/failover design needs separate release-specific verification and recovery testing; support for external PostgreSQL/Redis alone does not prove HA. [Connect workers](https://www.inngest.com/docs/durable-execution/deploying-functions/connect), [self-hosted architecture/configuration](https://www.inngest.com/docs/self-hosting).

**4. Add web hosts only with shared-state preparation.** Several users can retain private filesystem receipts while web/worker remain on one host. Before moving either across hosts, select shared storage or private object storage behind `BlobStoragePort`; local volumes do not become cross-host storage automatically. Preserve authorized downloads and approval + seven-day expiry across originals, temporary files, backups and object versions. In S3, a simple delete on a versioned bucket creates a delete marker; permanent removal needs version deletion. An eventual lifecycle rule alone does not establish the required physical deletion deadline. [Docker volume scope](https://docs.docker.com/engine/storage/volumes/), [S3 version deletion](https://docs.aws.amazon.com/AmazonS3/latest/userguide/DeletingObjectVersions.html).

For Next.js replicas behind a load balancer, deploy the same build, share the Server Action encryption key when using Actions, coordinate any enabled server caches/invalidation, and address rolling-deployment skew with the documented deployment ID behavior. Keep protected financial responses out of shared caches and retain versioned HTTP outbox replay. Defer an application read cache until profiling justifies one; the current Redis remains Inngest infrastructure. [Next.js multi-server guidance](https://nextjs.org/docs/app/guides/self-hosting#multi-server-deployments).

Retain Terraform's AWS + Docker providers on Mac/AWS: model explicit web/worker replica resources (for example with `for_each`) and apply reviewed changes. Do not add an autoscaler that competes with Terraform for the same containers. Revisit runtime ownership separately if automated scheduling becomes necessary. Keep the tailnet access model until user reachability and Tailscale eligibility are reviewed; multi-user interest alone does not authorize public ingress or AWS spending. [Terraform resource instances](https://developer.hashicorp.com/terraform/language/meta-arguments/for_each), [Tailscale plans](https://tailscale.com/pricing).

For the initial single host, propose a bounded maintenance window: drain requests and workers, apply compatible schema changes, replace pinned images, then gate reopening on health and smoke checks. Keep the previous image available; application rollback requires a compatible schema and does not reverse financial writes. Prefer additive schema changes followed by later cleanup. Before running replicas, verify staged rollout, mixed-version behavior and offline replay; this research does not establish zero-downtime deployment. [Next.js deployment coordination](https://nextjs.org/docs/app/guides/self-hosting#multi-server-deployments).

## 2. Runtime topology and availability

**Proposed targets:** the same Terraform-managed container topology on the existing Mac and on one AWS EC2 instance. These are separate environments with separate data, secrets and state; no automatic Mac/AWS data synchronization or cross-host shared volume is proposed. On EC2, persistent container data must reside on deliberately mounted encrypted EBS storage, not a disposable container layer. Local Ollama remains optional on the Mac; do not assume an inexpensive EC2 instance can run the chosen vision model.

```text
Phone/desktop PWA ── private Tailscale HTTPS ── Next.js Node server
                                                   ├── Better Auth → local PostgreSQL volume
                                                   ├── private receipts volume
                                                   └── local Inngest event API :8288 (IDs only)

Local Connect worker ── private WebSocket ── local Inngest server :8289
       │                                           ├── SQLite volume (history/config)
       ├── same domain modules + PostgreSQL         └── Redis volume (queue/run state)
       ├── shared private receipts volume
       └── 9router on loopback
               └── permitted cloud model or local Ollama
```

Tailscale Serve shares a local application within the tailnet and supports HTTPS; the user's phone needs Tailscale connected. Serve is private, whereas Funnel publishes a service publicly. Keep Inngest APIs/dashboard, its Connect gateway, Redis, 9router and Ollama off public and tailnet ingress. Use loopback for native processes or an isolated container network; publish no orchestration ports externally. [Tailscale Serve](https://tailscale.com/docs/features/tailscale-serve).

Run Next.js and the Connect worker as separate supervised processes from the same codebase, alongside supervised Inngest and Redis services. Their database pools, shutdown handling and health checks need explicit configuration. Only the worker calls the AI adapter; the web request stores a capture and schedules work. This is the recommended execution boundary, rather than adding another independently deployed API application.

Send attachment/proposal IDs in Inngest events, and return IDs/status from durable steps. The worker retrieves image bytes from private storage as needed. Inngest checkpoints completed step results, so returning a receipt image or full extraction would create an additional retained copy. Set application payload bounds independent of any hosted plan. [Workflow checkpoints](https://www.inngest.com/docs/durable-execution/durable-workflows).

**Host availability is a product limitation:** online writes and fresh reads require the selected app host. Mac sleep affects a Mac-hosted environment; an AWS deployment can avoid dependence on the Mac being awake if all required services, including its inference path, are available there. An installed, previously cached PWA can queue captures and show saved snapshots; first-time login/install requires connectivity. When the selected host sleeps, stops or fails, the app, worker, orchestration server and scheduler stop. Scheduled work is delayed; do not assume missed cron triggers replay automatically. Add startup reconciliation for unprocessed captures, due occurrences, expired attachments and missing reports, with bounded retry and visible pending/error states. Do not assume a failed event remains retryable indefinitely.

### Self-host configuration and recovery proposal

Use `inngest start` for production, reserving `inngest dev` for development. The single binary serves API/dashboard on `8288` and Connect on `8289`. Its default SQLite path is `.inngest/main.db`; embedded in-memory Redis queue/state is periodically snapshotted there. External `--redis-uri` and `--postgres-uri` are supported. [Self-hosting configuration](https://www.inngest.com/docs/self-hosting).

**Proposed persistence:** retain SQLite on a dedicated persistent volume; configure `--redis-uri` for dedicated local Redis on its own volume. Use Redis AOF with `appendfsync everysec` plus periodic RDB snapshots. This adds one small service while avoiding dependence on embedded queue snapshots alone. Redis describes a possible loss of approximately one second of writes with this AOF policy; it is not a zero-loss guarantee. [Redis persistence](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/). These stores hold orchestration data, not the financial ledger in application PostgreSQL. Retain this proposed SQLite + Redis arrangement when adding PostgreSQL for the app. Inngest can later use a separate PostgreSQL database with separate credentials if consolidation is justified; it is not part of this change.

Set SDK `INNGEST_DEV=0`, `INNGEST_BASE_URL=http://inngest:8288`, `INNGEST_EVENT_KEY` and `INNGEST_SIGNING_KEY`; configure matching server keys. The signing key must be even-length hexadecimal. These hostnames assume an isolated container network; use loopback equivalents for native processes. [SDK self-host configuration](https://www.inngest.com/docs/self-hosting#configuring-inngest-sdks-to-use-self-hosted-server). Set worker `gatewayUrl: "ws://inngest:8289/v0/connect"`. [Self-hosted Connect](https://www.inngest.com/docs/durable-execution/deploying-functions/connect#self-hosted-inngest). Replace the architecture's `/api/inngest` serve entry point with this worker entry point when implementing the adopted topology.

Keep keys server-side in restricted configuration outside version control; define rotation and test reconnection. Pin server, Redis and SDK releases. Start persistence services before Inngest and the worker; use health checks, graceful shutdown and restart supervision. Choose conservative worker concurrency after measuring the host. These are proposed operating requirements, not a tested deployment.

Back up SQLite and Redis as a coordinated recovery set using a documented quiesce/backup procedure; encrypt off-host copies and restore-test both stores with the pinned versions. Keep this separate from ledger and receipt backups. Reconcile captures and due work from authoritative application records after recovery; idempotency must tolerate repeats and lost recent queue state. Define bounded workflow-history retention and verify the selected server's supported cleanup mechanism before release. Monitor disk growth, backup age, queue age and worker connectivity; do not assume history expires automatically. Keep images and full extractions out of events, step outputs and diagnostic logs so orchestration history/backups do not become extra receipt archives.

## 3. Data correctness and authorization

Use TypeScript `bigint` and Postgres `bigint` for the locked minor-unit representation; carry `currency` with every amount. At JSON boundaries, send a signed decimal integer **string**, such as `"4500000"`, and reconstruct `bigint` after validation. Native JSON serialization rejects JavaScript BigInt. Keep localized input parsing deterministic and avoid converting ledger amounts to floating-point numbers for calculations. [Postgres numeric types](https://www.postgresql.org/docs/current/datatype-numeric.html), [BigInt JSON behaviour](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/BigInt#use_within_json).

The ledger module must commit postings, audit records and command idempotency atomically. Proposal approval must atomically update the proposal and its resulting transaction, including the attachment approval timestamp. A normal row `CHECK` cannot enforce a sum across every posting; design a reviewed deferred constraint trigger or controlled write procedure alongside transaction-level checks. Include unique keys for command replay and recurring occurrences. [Drizzle transactions](https://orm.drizzle.team/docs/transactions), [Postgres CHECK limitations](https://www.postgresql.org/docs/current/ddl-constraints.html), [constraint triggers](https://www.postgresql.org/docs/current/sql-createtrigger.html).

**Application authorization:** Better Auth stores sessions in PostgreSQL and exposes server-side `getSession` for Next.js. Validate the session on every protected route/action and attachment request, then require its authenticated user ID to match the explicitly provisioned owner mapping. A successful Google login alone grants no financial access. Keep credentials server-only, use secure cookies over HTTPS, and keep authenticated responses out of shared caches. Disable optional session cookie caching initially so revocation checks reach the session store. [Session management](https://better-auth.com/docs/concepts/session-management), [Next.js integration](https://better-auth.com/docs/integrations/next).

Provision a stable application owner UUID independently of Better Auth's user ID. Explicitly map the allowed Google provider subject → Better Auth user ID → application owner UUID; domain `user_id` columns and offline namespaces retain that UUID. Google documents `sub` as stable, while email can change. Pin the owner during trusted setup, reject other subjects at sign-in and at application entry points, and disable unrelated sign-up/linking paths. Never let the first arbitrary login claim ownership, derive UUIDs from email, or trust request-supplied identity. Verify OAuth callback registration against the actual HTTPS URL, consent configuration and owner sign-in before adopting this flow. [Google OpenID Connect](https://developers.google.com/identity/openid-connect/openid-connect), [Better Auth Google](https://better-auth.com/docs/authentication/google).

**Database defense in depth:** use separate migration credentials and a non-owner application runtime role without superuser or `BYPASSRLS`. Enable RLS on financial tables with `USING` and `WITH CHECK` against a transaction-local verified application owner context; missing/invalid context must deny access. Set context only after session/owner validation, on the same pooled connection and transaction as all protected queries; `set_config(..., true)` is transaction-local. Auth-table access needs a separately scoped role/schema so session lookup can occur before domain context exists. Jobs derive the fixed configured owner and validate record ownership rather than trusting event `user_id`. This protects against missing query filters; context set by the application is not a defense against compromise of that application or its DB credentials. Real PostgreSQL tests must prove fail-closed behavior and no context leakage across pooled connections. [Row security](https://www.postgresql.org/docs/current/ddl-rowsecurity.html), [configuration functions](https://www.postgresql.org/docs/current/functions-admin.html#FUNCTIONS-ADMIN-SET).

**Private receipt adapter:** use opaque generated keys with controlled paths, validate image type/size, strip metadata as already required, and prevent traversal/symlink escape. Write to a temporary file and rename into place; reconcile orphan files after failed DB commits. Only the authenticated application route resolves attachment IDs to files after checking owner and `expires_at`; send private/no-store responses and never put receipt bytes into service-worker or query caches. Filesystem APIs provide file operations, not authorization. [Node filesystem API](https://nodejs.org/api/fs.html), [OWASP upload guidance](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html).

Mount the same receipt volume into web and worker containers with restrictive ownership. Web needs upload/read access; extraction needs read access, and the cleanup worker needs delete access. Prefer a read-only extraction mount if cleanup is split later. Keep PostgreSQL data mounted only in its database container; workers use scoped DB connections, not raw database files. Neither orchestration nor 9router needs the receipt volume: the worker supplies bounded image bytes to the AI adapter. [Docker volume sharing and read-only mounts](https://docs.docker.com/engine/storage/volumes/).

## 4. Offline and AI boundaries

Cache the app shell with a service worker; persist only the read snapshots needed for offline screens. Show when those snapshots last synced. The command outbox owns a stable client command ID, payload version, pending/error status and retry metadata; only a durable server acknowledgement removes a command. Replaying the same ID must return the existing result, including after a timeout where the first write succeeded.

Background Sync has limited browser availability and requires a secure context. Flush on app startup, foreground return, online events and an explicit retry action; treat Background Sync as an enhancement. IndexedDB can face quota errors and eviction, so request persistent storage where supported, cap queued image size/count and report storage failures before claiming a capture was saved. [Background Sync](https://developer.mozilla.org/en-US/docs/Web/API/Background_Synchronization_API), [browser quotas and eviction](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria).

Keep the offline queue separate from disposable query snapshots; the server ledger remains authoritative. Namespace both by authenticated owner UUID, and never flush an earlier session's queue under a different identity. On logout or account change, clear financial read caches and expose an explicit decision for unsynced captures; silently deleting pending financial input would lose work. Shared-device support needs separate review because an authenticated server cannot retract a snapshot already stored on a device.

Receipt extraction has no ledger-write tools. It returns an untrusted proposal; deterministic code validates the shape, owner references, amount arithmetic, duplicates and allowed transitions before the user approves it. AI SDK structured output can help validate shape, but model capabilities differ; fallback must never turn a failed extraction into an assumed successful transaction. [Structured output](https://ai-sdk.dev/docs/ai-sdk-core/generating-structured-data), [compatible-provider capabilities](https://ai-sdk.dev/providers/openai-compatible-providers).

Retain the architecture's `AiGatewayPort` and deterministic test adapter. Send inline image data only after testing the installed 9router/model path; verify schema handling, timeout/fallback and error classification as a small adapter contract test. 9router documents `X-9Router-Token-Saver: off`; use it to avoid request rewriting, without treating it as protection against malicious instructions in receipts. Pin the router release, disable request-body debug logging, and keep its credentials outside the app database. [9router documentation](https://github.com/decolua/9router).

**Proposed inference policy:** permit only explicitly configured free-tier APIs and/or local Ollama through 9router; exhaustion leaves work pending for retry or manual entry. Never silently fall back to a paid model. The router's provider list does not establish an upstream provider's permission, privacy terms or cost. For a receipt that must remain on-device, use a local-only Combo with cloud fallback disabled. Actual model choices, receipt accuracy and acceptable provider data use remain review items; this research made no provider calls.

## 6. Terraform on Mac and AWS

**Recommendation:** use Terraform consistently for both targets, as requested. The AWS provider manages the cloud host; `kreuzwerker/docker` manages containers on either Docker engine. This is feasible because the Docker provider manages engine resources through the Docker API. For a Mac-only stack it adds state and planning overhead, but sharing one runtime definition across Mac and EC2 makes that tradeoff reasonable here. Terraform owns declared resources; Docker handles ongoing container execution. [Docker provider](https://registry.terraform.io/providers/kreuzwerker/docker/latest/docs).

### Ownership and reusable structure

| Root / owner | Proposed scope | Boundary |
|---|---|---|
| `mac-runtime` / Docker provider | Shared runtime module: images, application, PostgreSQL, Inngest, Connect worker, Redis, 9router, private Docker network and persistent volumes | Configure the Mac engine endpoint/context explicitly. A working engine, such as Docker Desktop, is a local prerequisite; Terraform does not install or start the Mac engine. [Docker provider configuration](https://registry.terraform.io/providers/kreuzwerker/docker/latest/docs), [Docker Desktop on Mac](https://docs.docker.com/desktop/setup/install/mac-install/). |
| `aws-infra` / AWS provider | VPC/subnet/routes, security groups, EC2, encrypted persistent EBS volume/attachment and scoped IAM profile where needed | Declare Docker installation, disk mounting and daemon startup through a reviewed machine image or EC2 cloud-init/user data. Cloud-init performs host setup; Terraform provisions its inputs. [AWS provider](https://registry.terraform.io/providers/hashicorp/aws/latest/docs), [EC2 user data](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/user-data.html). |
| `aws-runtime` / Docker provider | The same runtime module, targeting the prepared EC2 Docker engine | Apply only after bootstrap, durable mounts and authenticated engine access are verified. Instance creation alone does not establish runtime readiness. |
| Drizzle / application operations | Migrations, owner provisioning, backup/restore and receipt cleanup | Keep these explicit operations; Terraform container creation does not migrate or restore financial data. |

These are proposed logical roots, not files created by this research. Configure providers in the roots and pass them to the shared module; vary endpoint, storage paths, image architecture and resource limits without duplicating service definitions. Give each root its own state/backend key and credentials. Do not combine Mac and AWS resources in one state, and keep AWS infrastructure separate from runtime so the Docker endpoint exists before runtime planning. This split also requires an explicit sequence for host replacement: preserve storage, prepare the new engine, then reapply runtime against it. [Provider/module configuration](https://developer.hashicorp.com/terraform/language/modules/develop/providers).

Use the Mac's actual Docker socket/context rather than assuming `/var/run/docker.sock`. For EC2, use the provider's `ssh://` endpoint over a reachable restricted administration path, preferably the private tailnet; preserve SSH host-key verification. The SSH account needs Docker socket permissions, which confer substantial host control. Do not expose an unauthenticated/public Docker TCP API or mount its socket into application containers. [Provider connection options](https://registry.terraform.io/providers/kreuzwerker/docker/latest/docs), [Docker daemon access](https://docs.docker.com/engine/security/protect-access/).

Keep application/database ports closed to unsolicited public ingress and expose Next.js through Tailscale. Outbound access is needed for image pulls, Tailscale, Google OAuth and configured AI APIs. A public subnet with restricted ingress is possible; a private subnet needs an outbound path whose cost must be assessed. Provisioning/admin access must work before tailnet enrollment; do not assume Tailscale or SSM is already usable during bootstrap. [Internet gateway routing](https://docs.aws.amazon.com/vpc/latest/userguide/VPC_Internet_Gateway.html), [VPC pricing](https://aws.amazon.com/vpc/pricing/).

### Readiness, updates and persistent data

Declare health checks and bounded `wait = true` / `wait_timeout` on relevant containers; waiting requires a health check. Order dependent creation after healthy persistence services. Docker restart policies handle process exits and daemon restarts; Terraform is not a continuously running supervisor, scheduler or hot-reload tool. Dependencies do not replace application retries/reconnection, and an unhealthy live process needs monitoring/recovery beyond a restart-on-exit policy. [Container resource](https://registry.terraform.io/providers/kreuzwerker/docker/latest/docs/resources/container), [Docker restart policies](https://docs.docker.com/engine/containers/start-containers-automatically/).

Pin provider versions and commit the lockfile; select immutable image digests and compatible Mac/EC2 architectures. Build app/worker artifacts explicitly and review runtime plans when updating them. `docker_image` supports building/pulling, but a mutable tag alone does not automatically pull new layers. Local development can use a bind-mounted source tree and the Node development watcher inside Terraform-managed containers; do not apply Terraform for each source edit. [Image resource](https://registry.terraform.io/providers/kreuzwerker/docker/latest/docs/resources/image).

Persist PostgreSQL, receipts, Inngest SQLite and Redis independently of replaceable containers. On AWS, put their storage on the separately managed EBS disk and fail daemon/service startup when that mount is absent. Reattach and verify the disk before runtime recreation; never fall back silently to empty directories on the instance root disk. Review replacements and restore-test independent backups.

Use Terraform `lifecycle.prevent_destroy` on persistent Docker volumes and EBS resources, with explicit deletion procedures. `docker_volume` creates **and destroys** volumes; it has no `keep_locally` option. That option belongs to `docker_image` and preserves an image, not financial data. The lifecycle guard blocks planned deletion/replacement while configured, but removing the resource block removes its protection; it cannot prevent manual deletion or disk failure. Destruction of a disposable environment therefore needs a deliberate data-retention decision. [Volume resource](https://registry.terraform.io/providers/kreuzwerker/docker/latest/docs/resources/volume), [Image resource](https://registry.terraform.io/providers/kreuzwerker/docker/latest/docs/resources/image), [Lifecycle reference](https://developer.hashicorp.com/terraform/language/meta-arguments/lifecycle).

### State and secrets

Container environment values supplied through `docker_container.env` become Terraform-managed resource data; secret variables, secret-manager lookups and `sensitive = true` do not by themselves keep those values out of plans/state. Do not promise secret-free state for this provider. Prefer restricted host-side secret files mounted into containers, with applications/entrypoints reading them at runtime; Terraform should manage file paths/mounts rather than secret contents or uploaded secret files. Stage and rotate those files outside Terraform state and verify each service supports the chosen file-loading mechanism. This reduces state exposure, not host-administrator access. Ephemeral/write-only features help only where the actual provider argument supports them. [Container resource](https://registry.terraform.io/providers/kreuzwerker/docker/latest/docs/resources/container), [Terraform sensitive data](https://developer.hashicorp.com/terraform/language/manage-sensitive-data).

Exclude state, plans and credentials from Git; restrict access and encrypt storage/backups. Mac runtime can initially use local state on encrypted storage with a recoverable protected backup. Propose separately bootstrapped private S3 storage for the two AWS states, separate keys, encryption, versioning, least-privilege access and `use_lockfile = true`; include backend costs. Keep deployment state independent of the EC2 host. State records resource ownership, not a backup of ledger or receipt contents. [S3 backend](https://developer.hashicorp.com/terraform/language/backend/s3).

No infrastructure files, provider installation, plan, apply or deployment are included. There is no existing Compose deployment being migrated by this research; the proposed runtime owner is Terraform on both targets.
